# EEZ cross-chain devnet (Kurtosis)

A private Ethereum L1 running **two peered EL+CL pairs on one chain**, so a
single harness exercises both halves of an EEZ node at once — entirely inside
**one Kurtosis enclave**.

- **Pair B** — a vanilla reth + Lighthouse validator set, plus rbuilder, a
  flashbots relay, mev-boost, and spamoor, all run by
  [ethpandaops/ethereum-package](https://github.com/ethpandaops/ethereum-package).
  This is the block-builder / MEV side of the chain; it proposes every block.
- **Pair A** — `eez-node`'s **embedded** reth (`EEZ_L1_EMBEDDED=1`) plus a
  beacon-only follower Lighthouse that feeds it blocks. The embedded L1 gives
  `EvmComposer` in-process state access, which is what makes cross-chain
  composition possible.

Both ELs sit on the **same** chain (one shared genesis, `CHAIN_ID=7331`).
Every slot: rbuilder builds a block that includes `eez-node`'s bundle, a Pair B
validator proposes it, it gossips to the follower over the CL P2P network, and
the follower drives it into `eez-node`'s embedded reth via the engine API — so
the composer settles against real L1 state, in-process.

## Architecture

```
                    ONE L1 chain (CHAIN_ID 7331, genesis generated by Kurtosis)
  ┌──────────────────────────── ONE Kurtosis enclave (eez-devnet) ─────────────────────────────┐
  │  ┌──────────── Pair B (ethereum-package) ────────────┐   ┌──────── Pair A ────────┐         │
  │  │  reth ──engine── lighthouse (validators)          │   │  eez-node (one service):│        │
  │  │   ▲ builds        │ proposes rbuilder's block      │   │  ┌───────────────────┐  │        │
  │  │  rbuilder ◄─┐     ▼                                │   │  │ embedded L1 reth   │  │        │
  │  │  (el-5)     │   mev-boost-relay ◄── mev-boost      │   │  │  :18545 rpc         │  │        │
  │  │   ▲         │                                       │   │  │  :18551 engine(JWT)│  │        │
  │  │   │ eth_sendBundle (http://el-5…:8645)              │   │  └───┼───────────────┘  │        │
  │  │   └─────────┼───────────────────────────────────────┼───┤  ┌───┴──────────────┐  │        │
  │  │  spamoor (L1 load)   disruptoor (reorgs)            │   │  │ EvmComposer       │  │        │
  │  │                        block gossips over CL P2P ───┼──►│  │ (in-process reads)│  │        │
  │  └─────────────────────────────────────────────────────┘   │  │ Sequencer/Submit  │  │        │
  │                                                              │  └───┬──────────────┘  │        │
  │                                                              │  ┌───┴──────────────┐  │        │
  │                                                              │─►│ follower lighthouse│ │       │
  │                                                              │  │ (no validators)   │  │       │
  │                                                              │  └───────────────────┘  │       │
  │                                                              │  L2 rollup reth :18688  │       │
  │                                                              └─────────────────────────┘       │
  └────────────────────────────────────────────────────────────────────────────────────────────┘
   Services reach each other by enclave DNS (el-1-reth-lighthouse, eez-node, …) on fixed ports.
```

Per slot: users hit the L2 → composer builds an L2 batch → the Submitter sends
`[postBatch, …]` as an `eth_sendBundle` to rbuilder → rbuilder includes it →
the relay serves the block to a proposer → the proposed block gossips to the
follower → the follower feeds it to the embedded reth via `engine_newPayload`
→ the composer confirms settlement and advances the L2 safe head.

## What's in this directory

- [`main.star`](main.star) — the Kurtosis package. Brings up Pair B via
  `ethereum_package.run()`, deploys the EEZ contracts + L2 genesis onto it,
  then starts `eez-node` and the follower as two more services in the same
  enclave.
- [`args.example.yaml`](args.example.yaml) — the config template, in two
  blocks: `ethereum_package:` (passed straight through to the package) and
  `eez:` (images, keys, timing for Pair A).
- [`up.sh`](up.sh) / [`down.sh`](down.sh) — build the images and bring the
  enclave up / tear it down.
- [`deploy.Dockerfile`](deploy.Dockerfile) — the image that deploys the EEZ
  contracts onto the shared L1 as part of bring-up.
- [`scripts/enclave-env.sh`](scripts/enclave-env.sh) — resolves the enclave's
  RPC / disruptoor / builder URLs for the host-side helper scripts below.
- [`scripts/reorg-scheduler.sh`](scripts/reorg-scheduler.sh) — drives
  scheduled L1 reorgs via disruptoor.
- [`scripts/smoke-rbuilder.sh`](scripts/smoke-rbuilder.sh) — checks that
  rbuilder honors the bundle timestamp pin.

## Prereqs

`kurtosis`, `docker`, `cast` (from [Foundry](https://getfoundry.sh)). Works on
macOS or Linux.

## Run

```bash
bash infra/kurtosis/up.sh
```

That's the whole bring-up. On first run it will:
1. create `infra/kurtosis/args.yaml` from `args.example.yaml`,
2. derive the poster and proof-signer keys automatically from
   ethereum-package's standard prefunded dev mnemonic — no manual key step,
3. build the `eez-node` and `eez-deploy` images,
4. run `kurtosis run` to bring up both pairs in one enclave.

Later runs reuse `args.yaml` as-is and just rebuild the images.

**Env knobs** (all optional):

| Variable | Effect |
|----------|--------|
| `EEZ_SKIP_NODE_BUILD=1` | Reuse an existing `eez-node` image |
| `EEZ_SKIP_DEPLOY_BUILD=1` | Reuse an existing `eez-deploy` image |
| `EEZ_OPTIMIZED_BUILD=1` | Full release-profile `eez-node` build (slower) |
| `KURTOSIS_ENCLAVE=name` | Enclave name (default `eez-devnet`) |

Pass a different args file as the first argument:

```bash
bash infra/kurtosis/up.sh infra/kurtosis/args.yaml
```

**Teardown** (removes the whole enclave — no host process or on-disk artifacts
to clean up separately):

```bash
bash infra/kurtosis/down.sh
```

## Verify it's up and settling

```bash
E=eez-devnet

# all services present:
kurtosis enclave inspect $E

# L1 is producing blocks:
cast block-number --rpc-url "http://$(kurtosis port print $E el-1-reth-lighthouse rpc)"

# eez-node's embedded L1 tracks it (embedded L1 RPC is loopback-only, so read from logs):
kurtosis service logs $E eez-node | grep -i latest_number | tail

# cross-chain composer alive:
kurtosis service logs $E eez-node | grep -i "cross-chain EvmComposer constructed"

# settlement landing (allow a couple minutes after startup for MEV warmup):
kurtosis service logs $E eez-node | grep -iE "advanced L2 safe head" | tail

# count settled batches:
kurtosis files download $E eez-deployments /tmp/dep && set -a && . /tmp/dep/deployments.env && set +a
EL="http://$(kurtosis port print $E el-1-reth-lighthouse rpc)"
cast logs --from-block "$EEZ_REGISTRY_DEPLOY_BLOCK" --address "$EEZ_REGISTRY_ADDRESS" \
  "BatchPosted(uint256)" --rpc-url "$EL" --json | jq length

# rbuilder timestamp-pin check:
bash infra/kurtosis/scripts/smoke-rbuilder.sh
```

`smoke-rbuilder.sh` and `reorg-scheduler.sh` auto-discover RPC / builder /
disruptoor URLs via [`scripts/enclave-env.sh`](scripts/enclave-env.sh)
(`kurtosis port print` + keys from `args.yaml`).

## Full cross-chain end-to-end test

Two harnesses attach to the running enclave (they launch nothing) and are
entirely self-contained: each resolves its own endpoints via
`kurtosis port print` and its own protocol deployment via
`kurtosis files download`, so there's no separate discovery step — just bring
the enclave up and run the script.

- [`infra/kurtosis/devnet-test.sh`](devnet-test.sh) — **inbound-only** (L1→L2).
  Deploys Value on L2, creates setter + deposit CrossChainProxies on the shared
  L1, fires setter/deposit waves at the **L1 front**, and asserts L1
  `rollups(id).stateRoot` matches L2's actual state root with zero divergence.

  ```bash
  bash infra/kurtosis/devnet-test.sh
  ```

- [`infra/kurtosis/wave-test.sh`](wave-test.sh) — the comprehensive harness.
  `EEZ_WAVE_MODE` = `inbound` | `outbound` | `mixed` | `mixed-pure` exercises
  L1→L2 **and** L2→L1 (via the L2 front), direct + wrapper, with the wave loop
  and assertions in [`wave-lib.sh`](wave-lib.sh).

  ```bash
  EEZ_WAVE_MODE=mixed EEZ_WAVE_COUNT=3 bash infra/kurtosis/wave-test.sh
  ```

`devnet-test.sh` reads the composer log via `kurtosis service logs eez-devnet
eez-node` (a snapshot it refreshes itself; set `KURTOSIS_ENCLAVE` if you named
the enclave something else). `wave-test.sh` defers log handling to
`wave-lib.sh`; set `EEZ_NODE_LOG` to point it at a log file if you tee one
yourself. Cross-chain ops go to the fronts published by eez-node: `l1-xchain`
(Inbound) and `l2-xchain` (Outbound).

## Configuration

Everything is in [`args.example.yaml`](args.example.yaml), two blocks:

- **`ethereum_package:`** — participants, `mev_type`/`mev_params`,
  `spamoor_params`, `additional_services`. Passed straight to the package.
- **`eez:`** — Pair A's image tags, poster/proof-signer keys, timing
  (`l1_block_time_ms` must match `network_params.seconds_per_slot`), and L2
  genesis config.

Both pairs boot from the same generated genesis, so slot cadence and fork
schedule can never drift between them.

**Published ports** (host access via `kurtosis port print eez-devnet <service> <port-id>`):

| Service | Port id | In-container | Notes |
|---------|---------|--------------|-------|
| `el-1-reth-lighthouse` | `rpc` | 8545 | Canonical L1 JSON-RPC |
| `el-5-reth-builder-lighthouse` | `rbuilder-rpc` | 8645 | `eth_sendBundle` target |
| `eez-node` | `l2-rpc` | 18688 | L2 rollup JSON-RPC |
| `eez-node` | `l1-engine` | 18551 | Engine API (follower dials this) |
| `eez-node` | `l1-xchain` | 18999 | Cross-chain **Inbound** front (L1→L2); submit inbound ops here |
| `eez-node` | `l2-xchain` | 18998 | Cross-chain **Outbound** front (L2→L1); submit outbound ops here |
| `spamoor` | `http` | — | Load UI |
| `disruptoor` | `http` | — | Reorg primitive API |
| `assertoor` | `http` | — | Health assertions |
| `dora` | `http` | — | Block / reorg explorer |
| `forkmon` | `http` | — | Fork-choice monitor |

## Load and reorgs

### spamoor — continuous L1 load

Configured via `spamoor_params.spammers`. Rough throughput targets at 60M gas /
12s slots (~21k gas per `eoatx`):

| Target execution gas | `throughput` |
|-----------------------|--------------|
| ~10% | `280` |
| ~30% | `850` |
| ~50% | `1400` |

Set `throughput` in `args.yaml` and re-run `up.sh`, or tune live in the
spamoor UI (`kurtosis port print eez-devnet spamoor http`).

### disruptoor + reorg-scheduler — reorgs on demand

Disruptoor partitions the CL P2P network on command (needs `--privileged`,
which `up.sh` passes); healing lets fork-choice reorg out the losing side.
[`scripts/reorg-scheduler.sh`](scripts/reorg-scheduler.sh) drives it on a
schedule, splitting the network into a majority group (validators 1–3 + the
builder CL) and a minority group (validator 4 + the eez-node follower):

```bash
# Log intended partitions only, touch nothing:
EEZ_REORG_DRY_RUN=1 bash infra/kurtosis/scripts/reorg-scheduler.sh

# Default schedule: 1-block reorg every 20 blocks, 5-block every 100, 15-block every 1000:
bash infra/kurtosis/scripts/reorg-scheduler.sh

# Custom schedule (deepest match at a given height wins):
EEZ_REORG_SCHEDULES="shallow:1:20 medium:5:100 deep:15:1000" \
  bash infra/kurtosis/scripts/reorg-scheduler.sh
```

Other knobs: `EEZ_REORG_MAJORITY` / `EEZ_REORG_MINORITY` (comma-separated
service names), `EEZ_REORG_MIN_HOLD_S` (floor on how long the partition holds
before healing). The script always heals on exit, so Ctrl-C is safe.

To leave it running on an always-on box, detach it with `nohup`, `tmux`, or a
systemd unit.

### assertoor — automated bounds

`assertoor_params.run_stability_check` asserts reorg depth ≤2 and ≤2
reorgs/epoch; `run_block_proposal_check` asserts liveness. UI:
`kurtosis port print eez-devnet assertoor http`. During deliberate reorg
testing its stability check will flag the induced reorgs — that's expected.

### Monitoring

Dora and forkmon are enabled by default:

```bash
kurtosis port print eez-devnet dora http
kurtosis port print eez-devnet forkmon http
```

## Test scenarios

Suggested progression for exercising the pipeline end to end:

1. **Baseline** — no load, no partitions. Confirm the embedded L1 tracks the
   canonical chain and `BatchPosted` climbs every block.
2. **Load** — raise spamoor `throughput` toward your target blockspace
   utilization while confirming settlement keeps up.
3. **Shallow reorg** — run `reorg-scheduler.sh` with the default schedule.
   Confirm eez-node reorgs (`kurtosis service logs $E eez-node | grep -i reorg`)
   and settlement resumes immediately after.
4. **Deep reorg past a settled batch** — a longer hold / larger minority
   (`EEZ_REORG_MIN_HOLD_S`, `EEZ_REORG_MINORITY`) so the reorg reaches back
   past an already-`BatchPosted` block, exercising L2 retreat and re-derivation.
5. **Blobs across a reorg** — add a blob spammer (`scenario: blob-combined`)
   alongside the `eoatx` one, then run a reorg so blob-carrying blocks get
   orphaned.
6. **Bundle starvation** — push spamoor load high enough that relay block
   validation exceeds the slot time, so bundles miss their target block;
   confirm the composer retries cleanly instead of stalling.
7. **Concurrent submission + reorg** — run `infra/kurtosis/devnet-test.sh`
   while `reorg-scheduler.sh` is active, so a batch is in flight when its
   target block reorgs.
8. **Soak** — leave spamoor and the reorg scheduler running for an extended
   period; confirm no divergence accumulates over many cycles.
